## Целевая архитектура URL

Для SEO языки не переключаются JavaScript-ом на одной и той же странице: у каждой версии собственный URL и собственный HTML.

```text
https://example.com/              → 301 на основной язык (решить: /ru/ или /uk/)
https://example.com/ru/           → русская главная
https://example.com/uk/           → украинская главная
https://example.com/en/           → английская главная
https://example.com/es/           → испанская главная

https://example.com/ru/materials/
https://example.com/ru/materials/development/
https://example.com/ru/materials/development/landing-ili-sait/
```

Та же структура повторяется для `uk`, `en`, `es`. У каждого документа:

- self-canonical на собственный URL;
- `hreflang` на все реально существующие переводы и `x-default`;
- один H1;
- без URL с `?lang=`, дублей с `/index.html`, смешения языков или автоматического редиректа поискового робота по IP.

Статус: **готово**. Корень редиректит на `/ru/` и остаётся `x-default`.

## День 1 — контент, локализация, SEO-фундамент

### 1. Локализация

Статус: **технически готово; редакторская вычитка UK/EN/ES — после запуска или перед рекламным трафиком.**

- вынести все пользовательские строки из HTML/JS в единый словарь;
- подготовить RU, UA, EN, ES без машинно-переведённых смешанных фрагментов;
- перевести title, description, Open Graph, alt, хлебные крошки, CTA, форму, 404 и cookie-баннер;
- создавать отдельные файлы/маршруты для языков, а не только менять текст в браузере;
- проверить, что язык `lang` у HTML соответствует странице: `ru`, `uk`, `en`, `es`.

Статьи пока можно считать русскими черновиками. Нельзя ставить `hreflang` на страницу, которой ещё нет: до готовности перевода оставляем только существующие языковые варианты.

### 2. Техническая SEO-проверка

Статус: **основная разметка готова; финальный визуальный и production QA — в очереди.**

Для каждой индексируемой страницы проверить:

- один H1, логичные H2/H3, без пустых заголовков;
- уникальные `<title>` и `<meta name="description">`;
- canonical с production-доменом;
- OG: `og:title`, `og:description`, `og:image`, `og:url`, `og:type`;
- Twitter Card;
- осмысленные `alt` у содержательных изображений; декоративные изображения — с пустым `alt`;
- внутренние ссылки только на реальные URL;
- доступность: видимый focus, семантические кнопки, подписи полей, контраст.

Schema.org:

- главная — `Organization` / `ProfessionalService`;
- каталог материалов — `CollectionPage`;
- статья — `Article` с автором, publisher, датой, изображением и языком;
- кейс — `CreativeWork` или `CaseStudy` через `CreativeWork`;
- хлебные крошки — `BreadcrumbList`.

### 3. Файлы для индексации

Статус: **готово**: `robots.txt`, `sitemap.xml`, локализованные `404.html`, видимая `sitemap.html`. XML sitemap содержит только 128 индексируемых canonical URL.

Создать в production-корне:

```text
/robots.txt
/sitemap.xml
/sitemap-ru.xml       (если sitemap разбивается по локалям)
/404.html
/privacy/
/cookies/             (если требуется отдельная страница)
```

`robots.txt` должен разрешать публичные страницы, закрывать служебные пути при их появлении и содержать ссылку на sitemap. В sitemap включать только canonical-URL со статусом 200; не включать редиректы, 404, дубли и будущие пустые переводы.

### 4. Правовые страницы и cookies

Статус: **privacy-шаблон создан; требуются реальные реквизиты оператора данных и cookie-consent.**

Подготовить:

- страницу политики конфиденциальности: какие данные собирает форма, цели, сроки, получатели, контакты оператора, права пользователя;
- cookie-баннер с категориями `necessary`, `analytics`, `marketing`;
- сохранение выбора пользователя;
- Analytics и рекламные пиксели загружаются только после соответствующего согласия, кроме строго необходимых cookies.

## День 2 — интеграции, инфраструктура, контроль

### 5. Формы и Telegram-бот

Статус: **серверная отправка реализована; требуется production-тест доставки и защиты от спама.**

Определить контракт заявки до подключения формы:

```text
source: website
locale: ru | uk | en | es
page_url: полный URL страницы
page_title: заголовок страницы
form: diagnostic | contact | article_cta
name: строка
company: строка (опционально)
contact: строка
message: строка (опционально)
consent: true
submitted_at: ISO-8601
```

Поток:

```text
Форма → защищённый endpoint Railway → валидация / rate limit / honeypot
      → Telegram Bot API → рабочий чат/топик
      → ответ пользователю + событие analytics
```

Не отправлять токен Telegram в клиентский JavaScript. Хранить `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` только в переменных окружения Railway. Проверить обработку ошибки: пользователю не обещается отправка, если сервер не принял заявку.

### 6. Аналитика

Статус: **ожидает идентификаторы GTM/GA4; Meta Pixel будет добавлен после получения Pixel ID.**

Базовый стек: GA4 + Google Tag Manager. Meta Pixel и рекламные теги — только с cookie-consent и при реальной необходимости.

Обязательные события:

| Событие | Параметры |
| --- | --- |
| `page_view` | `page_location`, `locale`, `page_type` |
| `cta_click` | `cta_name`, `destination`, `page_type`, `locale` |
| `form_start` | `form_name`, `page_url` |
| `form_submit` | `form_name`, `page_url`, `locale` |
| `form_success` | `form_name`, `locale` |
| `case_open` | `case_slug`, `position` |
| `article_open` | `article_slug`, `article_category` |
| `article_toc_click` | `article_slug`, `section_id` |
| `article_share_copy` | `article_slug` |
| `article_cta_click` | `article_slug`, `cta_type` |
| `next_article_open` | `from_article`, `to_article` |
| `article_read_75` | `article_slug` |
| `language_switch` | `from_locale`, `to_locale` |

Не передавать в аналитику имя, телефон, email, текст заявки или другие персональные данные.

### 7. Railway и Cloudflare

Статус: **домен, Cloudflare и Railway существуют; требуется финальная проверка production-редиректов, HTTPS и переменных окружения.**

Railway:

- создать production-сервис из репозитория и ветки `main`;
- определить build/start для статического сайта или Node-сервера с API форм;
- добавить переменные окружения для Telegram и будущих интеграций;
- включить HTTPS через custom domain;
- настроить healthcheck, если используется сервер.

Cloudflare:

- добавить домен, перенести DNS nameservers;
- создать DNS-записи, которые требует Railway;
- выбрать один канонический хост: `https://example.com` или `https://www.example.com`;
- настроить постоянный 301 со второго варианта на канонический;
- включить Full (strict) SSL, automatic HTTPS rewrites и кеширование статических ассетов;
- не кешировать HTML агрессивно до окончания активной отладки;
- после запуска проверить цепочки редиректов: HTTP → HTTPS, `www` ↔ apex, `/` → основной языковой URL.

### 8. Финальный QA перед DNS-переключением

Статус: **осталось выполнить на реальном production-домене.**

Проверить в Chrome, Safari/iOS, Firefox и на мобильной ширине:

- главная, кейс, каталог, раздел, статья, privacy, 404;
- все ссылки, изображения, якоря, share-кнопки и CTA;
- язык и URL после перехода;
- формы: успешная отправка, ошибка, спам-поле, Telegram-уведомление;
- consent: до согласия теги не загружены; после — загружены согласно выбору;
- Lighthouse / PageSpeed: mobile и desktop;
- Rich Results Test для Article и Organization;
- Search Console URL Inspection для главной, кейса и статьи;
- sitemap доступен и принят;
- в GA4 DebugView приходят `page_view`, CTA и form events.

## Критерии «можно запускать»

- все production URL отдают 200, а дубли — только 301 на canonical;
- языковые страницы имеют корректные `lang`, canonical и `hreflang`;
- `robots.txt`, sitemap, 404, privacy и cookie-consent опубликованы;
- нет сломанных ссылок, пустых `alt` у смысловых изображений и заголовков вне иерархии;
- форма доставляет тестовую заявку в Telegram и не раскрывает секреты в браузере;
- аналитика фиксирует ключевые действия без персональных данных;
- DNS, HTTPS и редиректы Cloudflare/Railway проверены;
- Search Console и GA4 созданы и доступны владельцу.
